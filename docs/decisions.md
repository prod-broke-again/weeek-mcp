# Архитектурные решения WEEEK MCP Server (`weeek-mcp`)

В этом документе зафиксированы ключевые архитектурные и технические решения проекта `weeek-mcp-server`.

---

### Read-only режим по умолчанию для всех инструментов
**Решение:** Все MCP-инструменты сервера работают строго в режиме чтения (read-only). Любые модифицирующие операции закрыты флагом `WEEEK_ALLOW_WRITE=false`.  
**Почему:** Защита задач, досок и проектов WEEEK от случайного изменения или удаления AI-моделями во время автоматического анализа.  
**Что будет, если сделать иначе:** Ошибочный или галлюцинированный вызов инструмента может изменить приоритеты, статус или содержимое реальных задач в рабочей области.  
**Дата:** 2026-03-01

---

### Двухшаговое подтверждение любых изменений задач
**Решение:** Write-инструменты доступны только при `WEEEK_ALLOW_WRITE=true` и всегда работают по схеме `weeek_propose_*` → явное подтверждение пользователя отдельным сообщением → `weeek_confirm_write` с одноразовым токеном (TTL 10 минут). Propose не изменяет Weeek. Агенту явно запрещено создавать, редактировать, перемещать или удалять задачи по собственной инициативе.  
**Почему:** Текстовая инструкция снижает риск неправильного решения агента, а отдельный одноразовый токен механически исключает мутацию во время подготовки превью.  
**Что будет, если сделать иначе:** Агент сможет случайно выполнить действие до того, как пользователь увидит точные поля и подтвердит их.  
**Дата:** 2026-08-10

---

### Раздельные whitelist для чтения и записи проектов
**Решение:** `WEEEK_READ_ONLY_PROJECTS` ограничивает доступ на чтение; `WEEEK_WRITE_PROJECTS` — отдельный whitelist для `propose_*` / `confirm_write`. Пустой write-list при включённом `WEEEK_ALLOW_WRITE` означает «писать в любой читаемый проект».  
**Почему:** Нужно читать рабочие проекты (например #2) и писать только в бэклог (#5), без расширения write-поверхности на всё workspace.  
**Что будет, если сделать иначе:** Один общий whitelist либо запретит чтение нужных проектов, либо разрешит мутации вне бэклога.  
**Дата:** 2026-08-10

---

### Файловое хранилище pending write-токенов
**Решение:** При `WEEEK_ALLOW_WRITE=true` токены `propose → confirm` пишутся в `WEEEK_PENDING_WRITES_DIR` (по умолчанию рядом с session file), а не только в память процесса.  
**Почему:** Remote HTTP gateway (supergateway streamableHttp stateless) поднимает новый stdio-процесс на каждый запрос; in-memory Map делает `weeek_confirm_write` всегда «Unknown or already used».  
**Что будет, если сделать иначе:** Агенты смогут получать preview, но не смогут подтвердить ни одну мутацию через удалённый MCP.  
**Дата:** 2026-08-10

---

### Чтение комментариев задач через импортированную сессию браузера
**Решение:** Чтение комментариев к задачам выполняется через приватный API приложения (`api.weeek.net/ws/{workspaceId}/tm/tasks/{taskId}`) с использованием cookie сессии, хранимой в `~/.weeek-mcp/session.json`.  
**Почему:** Публичный WEEEK API v1 не предоставляет эндпоинты для комментариев к задачам, однако контекст обсуждений критически важен для AI-ассистентов.  
**Что будет, если сделать иначе:** Ассистент не сможет видеть историю обсуждений и уточнения по задачам, работая только с сухим описанием карточки.  
**Дата:** 2026-03-05

---

### Вывод логов исключительно в `stderr` через Pino
**Решение:** Настроить логгер `PinoLogger` на запись всех сообщений только в поток `stderr`.  
**Почему:** Протокол MCP stdio использует `stdout` исключительно для обмена сообщений JSON-RPC. Вывод произвольного текста в `stdout` ломает парсер транспортного слоя.  
**Что будет, если сделать иначе:** Сервер будет аварийно завершать работу и отключаться от Cursor / Claude Code при первой попытке записать лог.  
**Дата:** 2026-03-01

---

### Вендоринг OpenAPI-схемы и генерация DTO через `openapi-typescript`
**Решение:** Сохранять спецификацию WEEEK OpenAPI в `openapi/weeek.json` и автоматически генерировать TypeScript-типы (`src/infrastructure/weeek/dto/schema.ts`).  
**Почему:** Гарантирует строгую типизацию ответов и запросов WEEEK API на этапе компиляции без ручного поддержания интерфейсов.  
**Что будет, если сделать иначе:** Высокий риск ошибок из-за рассинхронизации ручных типов и фактических ответов API WEEEK.  
**Дата:** 2026-03-02

---

### In-Memory TTL-кэширование справочников и проектов
**Решение:** Использовать `TtlCache` для списков проектов, участников, тегов и колонок (TTL по умолчанию: 300 секунд).  
**Почему:** Снижает количество повторных сетевых запросов к WEEEK API и предотвращает превышение лимитов частоты запросов (`WEEEK_RPS=4`).  
**Что будет, если сделать иначе:** Медленная работа инструментов и регулярные ошибки `429 Too Many Requests` от сервера WEEEK.  
**Дата:** 2026-03-03

---

### Слоеная чистая архитектура (Domain / Application / Infrastructure / MCP)
**Решение:** Разделить доменные модели и интерфейсы репозиториев, прецеденты использования (use cases), клиенты WEEEK API и обработчики MCP-инструментов.  
**Почему:** Позволяет изолированно тестировать бизнес-логику и преобразования данных с помощью Unit-тестов без завязки на реальный SDK или API WEEEK.  
**Что будет, если сделать иначе:** Код станет монолитным и труднотестируемым, а изменения в MCP SDK затронут бизнес-логику работы с WEEEK.  
**Дата:** 2026-03-01

## Отвергнутые варианты

### Использование Puppeteer / Playwright для парсинга комментариев
- **Отвергнуто:** Добавление тяжелых бинарных зависимостей браузера существенно увеличивает размер пакета и время запуска MCP-сервера.
- **Альтернатива:** Прямой HTTP-запрос к приватному эндпоинту WEEEK с сохранёнными сессионными cookie.

### Выполнение записи (модификации tasks) через публичный API по умолчанию
- **Отвергнуто:** Неконтролируемая запись потенциально опасна при автономиях агента.
- **Альтернатива:** Строгий read-only режим по умолчанию с возможностью опционального переключения флага в будущем.
